# ADR 0021 — Generate schema docs with json-schema-for-humans

| **Status** | accepted |

## Context

[ADR 0020](0020-a-live-schema-viewer-is-not-a-generated-rendering.md) shipped
a live-fetching viewer: `schema-docs/index.html` plus a hand-written `app.js`
that fetched `index.json`, `metadata/*.json` and `layout/*.json` in the
browser, resolved `$ref` client-side, and rendered a field tree with plain
CSS, then Pico.css. Two rounds of hand-styling that field tree — plain CSS,
then Pico.css — still did not produce a result the person asking for it was
satisfied with; the complaint was never the page chrome, it was the
information-heavy field-tree rendering underneath.

Rather than attempt a third hand-styled round, real candidates were
researched and compared instead of guessing at another layout:

| Tool | Maintenance | Fit |
|---|---|---|
| [docson](https://github.com/lbovet/docson) | Last commit 2023-11-05, 44 open issues — effectively unmaintained | Architecturally the best fit: live, embed-a-script-tag, zero build. Too risky to depend on given the maintenance state. |
| [@cloudflare/doca](https://github.com/cloudflare/json-schema-tools) | Actively maintained (last push ~5 months before this ADR) | Built around JSON *Hyper-Schema*'s API-link extensions, which this repository's plain data schemas do not use. |
| [docusaurus-json-schema-plugin](https://github.com/jy95/docusaurus-json-schema-plugin) | Very actively maintained (87 stars, last push 2 days before this ADR) | Requires adopting the entire Docusaurus static-site framework (a Node/React build pipeline) to render two schema files. Also AGPL-3.0-or-later — acceptable for a dev-only tool, but worth naming given this repository's own unresolved licensing question ([open-items.md](../reference/open-items.md), item P10). |
| [json-schema-for-humans](https://github.com/coveooss/json-schema-for-humans) | 746 stars, last commit 2 weeks before this ADR | A real generator, not something built or maintained here: collapsible property tree, expand/collapse-all, breadcrumbs, tabbed `oneOf`/`anyOf`, automatic `$ref` resolution including circular refs. Chosen. |
| Keep hand-rolling `app.js` | — | Two rounds already did not satisfy; a third round spends more effort re-inventing what a maintained generator already does well. |

## Decision

**`schema-docs/generated/<spec>/<ver>/metadata.html` is generated by
[json-schema-for-humans](https://github.com/coveooss/json-schema-for-humans)
1.5.1, pinned in `schema-docs/requirements-dev.txt`, run by a new `just
schema-docs-gen` recipe** — the same shape as the existing `codegen` recipe:
a pinned dev-only requirements file, a loop over every version each spec's
`index.json` lists, and a `GENERATED -- do not edit by hand` marker on every
output file. `layout/<ver>.json` is not JSON Schema — it is a fixed,
permanently-simple `{specVersion, required, optional}` shape — so it is
never run through this tool; it stays a tiny hand-written two-column list on
`schema-docs/index.html`, unchanged in kind from what ADR 0020 already did
for it, just rendered by hand instead of fetched.

**Verified empirically before committing to this shape** (rule 5):

- A relative `$ref` into `schemas/common/` (`about`, `spatial-coverage`)
  resolves and renders inline **with no extra flag** — `generate-schema-doc`
  against `schemas/snapshot-spec/metadata/1.0.0.json` alone produced every
  field of `about` and reused `spatialCoverage` (which the snapshot spec's
  `.init` block does not `$ref` a second time, but the model input spec's
  `networks[].spatialCoverage` does) as a "Same definition as spatialCoverage"
  link rather than a duplicate render, via the tool's own
  `link_to_reused_ref`. This is unlike `datamodel-code-generator`, where
  `--allow-remote-refs` in the existing `codegen` recipe is load-bearing —
  the difference is that this `$ref` target is a local file path, not treated
  as a network fetch by either tool, so json-schema-for-humans needed nothing
  special to follow it.
- **Filename collisions are real and were reproduced.** Every
  `metadata/<ver>.json` and `layout/<ver>.json` in this repository is
  literally named `1.0.0.json`, in four different directories. Running
  `generate-schema-doc schemas/ <out>/` once (a naive glob over the whole
  tree) logged five separate "Generating 1.0.0.html" lines and left exactly
  one `1.0.0.html` file on disk — each generation silently overwrote the
  last. The fix is what `schema-docs-gen` does: invoke the tool once per
  input file, with an explicit output path that mirrors the source directory
  structure (`schema-docs/generated/<spec>/<ver>/metadata.html`), so no two
  outputs ever share a path.
- **Pointed at `layout/1.0.0.json` directly, the tool does not error — it
  produces a meaningless empty document** (title "Schema Docs", no
  properties, since `{specVersion, required, optional}` isn't a JSON Schema
  object with a `properties` keyword at all). Confirmed by generating it and
  reading the output, not assumed. This is why `layout/` is excluded by
  construction in `schema-docs-gen` rather than filtered after the fact.
- **The tool is not deterministic by default.** `footer_show_time` defaults
  to `true` and embeds a wall-clock timestamp in every page's footer
  (`Generated using json-schema-for-humans on 2026-09-24 at 23:44:07 +0900`).
  `schema-docs-gen` passes `--config footer_show_time=false`; with that set,
  two consecutive runs from a clean `schema-docs/generated/` produced
  byte-identical output (checked with `diff -r`), matching the same bar
  `codegen` already holds for its own generated files.
- CSS/JS the tool needs (`schema_doc.css`, `schema_doc.min.js`) are copied
  into each version's own output directory rather than shared across
  versions — the tool's `--no-copy-css`/`--no-copy-js` flags stop it copying
  them but do not add any way to point the HTML at a different relative
  path, and with two specs at one version each today the duplication is a
  few kilobytes. Not worth fighting the tool over.

**This ADR supersedes ADR 0020.** ADR 0020's decision — a live-fetching
viewer with no generated output — is not what ships any more; ADR 0018's
"no generated renderings" is now narrowed by this ADR instead, and 0020's own
header is marked superseded rather than rewritten (ADRs are append-only in
this repository). [ADR 0018](0018-shared-definitions-and-no-renderings.md)'s
`Amended by` row is repointed at this ADR, noting in passing that 0020 was an
intermediate step so that history is not lost.

## Alternatives considered

See the maintenance/fit table above for the four real candidates. In summary:
docson lost on maintenance risk, doca on being built for a different JSON
Schema dialect (Hyper-Schema), docusaurus-json-schema-plugin on requiring an
entire static-site framework for two files, and continuing to hand-roll
`app.js` on having already had two rounds fail to satisfy.

## Consequences

**A new local dev prerequisite**: Python plus `pip install -r
schema-docs/requirements-dev.txt`, the same shape the `codegen` recipe
already requires for `datamodel-code-generator` and `json2ts`.

**A manual "regenerate before republish" step.** Changing any
`metadata/<ver>.json` now means running `just schema-docs-gen` and
committing the result before publishing `schema-docs/` to S3 — the same
manual-publish pattern `schemas/` itself already uses, since no CI exists yet
to catch a forgotten regeneration (`ops/missions/README.md`'s **Next** item
1). `schema-docs/index.html`'s hand-written `index.json`/`layout/<ver>.json`
transcription needs the same manual update, by hand, in the same commit.

**The old `app.js`, under `schema-docs/`, is deleted**, fully superseded — nothing in
`schema-docs/` fetches or resolves `$ref` in the browser any more. Most of
the old hand-rolled `style.css` (the field-tree classes: `.field`,
`.nested-props`, `.combiner-label`, and the sidebar nav layout) is gone with
it; `index.html` is now small enough that a handful of rules on top of
Pico.css cover it.

`docs/architecture/repository-layout.md` and `docs/reference/s3-layout.md`
need updating to describe the new build step and stop describing
`schema-docs/` as fetch-only. Both are updated by this same change, listed
here as a consequence and made a task rather than left open.
